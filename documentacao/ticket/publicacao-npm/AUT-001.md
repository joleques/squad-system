# Automatizar publicação versionada do Squad System no npm

## Objetivo

Automatizar a publicação de novas versões do pacote `@joleques/squad-system` no npm após a criação e o envio de uma tag Git válida, eliminando a publicação manual e evitando tokens npm persistentes no repositório ou no GitHub.

## Contexto

A versão `1.0.0` foi publicada manualmente no npm e o pacote já está associado ao repositório `joleques/squad-system`. O próximo passo é tornar o release repetível, rastreável e seguro.

A solução deve usar npm Trusted Publishing com GitHub Actions e autenticação OIDC. Um `Makefile` deve oferecer comandos simples para preparar releases patch, minor e major.

## Escopo

- Incluído:
  - criar `Makefile` com comandos de teste, empacotamento e release;
  - suportar releases `patch`, `minor` e `major`;
  - atualizar a versão com `npm version`;
  - criar e enviar commit e tag Git de versão;
  - criar workflow GitHub Actions acionado por tags `v*`;
  - validar correspondência entre a tag e `package.json.version`;
  - executar testes e `npm pack --dry-run` antes da publicação;
  - publicar no npm com Trusted Publishing/OIDC;
  - gerar `package-lock.json` para execução determinística no CI;
  - documentar o processo de configuração e release.
- Fora de escopo:
  - armazenar `NPM_TOKEN` no repositório ou em arquivos `.env`;
  - publicar em outros registries;
  - gerar changelog automaticamente;
  - criar GitHub Release automaticamente;
  - publicar a partir de branches sem tag de versão.

## Definition of Done

- [ ] `make test` executa a suíte completa.
- [ ] `make pack` valida o conteúdo do pacote sem publicar.
- [ ] `make release-patch`, `make release-minor` e `make release-major` validam a árvore Git, atualizam a versão e enviam commit e tag.
- [ ] O workflow roda somente para tags no padrão `v*`.
- [ ] O workflow falha quando a tag diverge da versão do `package.json`.
- [ ] Testes e empacotamento passam antes de `npm publish`.
- [ ] A publicação usa OIDC com `id-token: write`, sem token npm persistente.
- [ ] O workflow usa runner hospedado pelo GitHub e versões de Node/npm compatíveis com Trusted Publishing.
- [ ] O README documenta preparação, configuração no npm e execução de releases.
- [ ] Testes automatizados protegem os contratos do Makefile e do workflow.
- [ ] Revisões de arquitetura e princípios de software aprovadas.

## Critérios de Aceite

- Dado um repositório sem alterações pendentes, quando `make release-patch` for executado, então a versão patch será incrementada e o commit e a tag correspondentes serão enviados ao GitHub.
- Dada uma tag `vX.Y.Z` compatível com `package.json.version`, quando o workflow executar e os gates passarem, então a mesma versão será publicada como `@joleques/squad-system@X.Y.Z`.
- Dada uma divergência entre tag e versão, quando o workflow executar, então a publicação será bloqueada com erro claro.
- Dada uma falha de teste ou empacotamento, quando o workflow executar, então `npm publish` não será chamado.
- Dado o workflow versionado, quando seus arquivos forem inspecionados, então nenhum token npm estará presente ou referenciado como segredo de publicação.
- Dada uma versão já publicada, quando houver nova tentativa com o mesmo número, então o fluxo falhará sem alterar a versão existente no npm.

## Configuração Externa Necessária

No pacote `@joleques/squad-system`, configurar um Trusted Publisher no npm:

- Provider: GitHub Actions
- Organization or user: `joleques`
- Repository: `squad-system`
- Workflow filename: `publish.yml`
- Allowed action: `npm publish`

## Lacunas e Perguntas Bloqueantes

Nenhuma para iniciar. A implementação deve confirmar na documentação oficial vigente as versões mínimas de Node, npm e actions antes de fixá-las no workflow.

## Impacto Esperado

- Novos arquivos: `Makefile`, `.github/workflows/publish.yml` e `package-lock.json`.
- Alterações esperadas: `README.md`, testes de distribuição e eventualmente scripts do `package.json`.
- Risco principal: publicação indevida por tag incorreta; mitigado pela validação tag-versão e pelos gates de teste e empacotamento.
- Risco de segurança: vazamento de credencial de longa duração; mitigado pelo uso exclusivo de Trusted Publishing/OIDC.
